Agentic Trader — Daily Operator Checklist Review & Automation Findings

Review basis: daily-operator-checklist.md, checked against the repository as described in that document on 23 October 2026. Times are IST.
Scope: This is a document-based operational review of the described local paper-trading application. It is not an independent code audit, broker certification, or evidence of strategy profitability.

Executive summary

Main finding: Automate repetitive checks, data validation, monitoring, reporting, and recovery evidence collection. Preserve explicit human authorization at safety-critical boundaries until the implementation has been tested and a clear authorization policy exists.

The checklist already describes meaningful safeguards: Manual mode during preparation, explicit setup acknowledgement, separate Approval and Automatic modes, quote-freshness checks, price-basis reviews, order/fill reconciliation, and database verification. It also documents important limitations: no full daily scheduler, no unattended refresh of installed strategy data, interrupted preparation is not resumed, setup phases can partially persist without automatic rollback, and the service/feed must remain available for protection and fills.

1. What the source checklist says

The uploaded checklist says:

  • It describes the existing local paper application, especially the long-term account opened by ./scripts/start_ui.sh; intraday has different close and warmup rules.
  • Fresh strategy data should be downloaded on each trading day the normal guided Strategies → reviewed strategy → Approval/Automatic workflow will be used.
  • The download is a research-input bundle. It does not itself install the strategy, change trading mode, update live subscriptions, or place orders.
  • Current-day source snapshots and explicit action/price-basis reviews matter even when the last completed candle has not changed.
  • The application does not currently have an unattended daily refresh or incremental update of an installed download.
  • The daily screen checks 20-session momentum, a 50-session trend, average daily turnover, and volatility. Thresholds stated in the checklist are positive momentum, at least ₹1 crore average daily turnover, and at most 5% daily volatility. Ranking by historical gross return is not a forecast.
  • The shortlist is limited to ten symbols and must retain held symbols; risk limits may permit fewer positions.
  • The built-in history bundle covers up to 60 completed sessions from at most 120 calendar days in the current year. It is insufficient for SMA200 and many longer weekly/monthly indicators; warmup states are expected.
  • Rules-only is described as an experimental paper hypothesis. ML requires a separately validated compatible model and does not silently fall back to rules.
  • Broker access token validity is separate from local dashboard unlock. The checklist describes next-day 6 AM token expiry as documented by Kite, with earlier invalidation possible.
  • A connected socket is not proof of usable quotes. Freshness, exchange time, basis state, and usable bid/ask depth must be checked.
  • Automatic mode may submit eligible paper orders without per-trade confirmation; Approval mode requires proposal review. Protective exits do not wait for Approval, but still depend on usable quotes and liquidity.
  • On a safety pause, the desk returns to Manual and pending approval authority is cancelled; restored quotes do not automatically rearm trading.
  • Long-term holdings intentionally persist overnight; the ordinary intraday 15:15 flatten is an exit request, not proof of a fill.
  • Reports and backups should use the same account configuration. The checklist warns that owning recovery commands can cancel pending order residue, so report first if preserving that state matters.
  • A database backup is not a full installation backup; configuration, calendar, strategy/data/model artifacts, and ledger need a deliberate backup policy.
  • The checklist states that no automatic daily scheduler performs the full checklist. Authentication/2FA, source review, confirmation, exception handling, and deliberate mode activation remain operator responsibilities.

3. Highest-priority automation proposals

P0 — Independent safety watchdog

Monitor service health, feed status, quote freshness, risk faults, pending protective exits, and account state independently of the browser UI. Send actionable alerts when protection is impaired.

Acceptance tests: kill the service; interrupt network; freeze quotes; provide stale timestamps; simulate empty bid/ask depth; create an unresolved exit. Confirm the system alerts, blocks new discretionary entries where appropriate, preserves state, and does not falsely report protection.

P0 — Daily preflight orchestrator

An IST-aware scheduler should identify supported exchange sessions and run read-only checks before any mutating setup phase. Validate broker session, source snapshots, latest completed candle, calendar, catalog mappings, held symbols, outstanding orders, and required reviews.

Output: a single report where every prerequisite is PASS, BLOCKED, or NEEDS REVIEW, with evidence timestamps and reason codes. A completed preflight must not automatically imply trading permission.

P0 — Order and position reconciliation

Reconcile order intent IDs, submission status, order IDs, fills, remaining quantities, fees, cash reservations, holdings, and exits. Treat timeouts as ambiguous until a status read resolves them.

Acceptance tests: full fill, partial fill, reject, cancel, delayed status, duplicate request, timeout after server acceptance, and restart during order handling. Never retry an uncertain submission without checking current state and idempotency.

P1 — Crash-safe setup and recovery

Persist every setup phase and its inputs/outputs under a unique run ID. On restart, inspect actual account state and the last committed phase. Resume only if the operation is safe and the state is verified; otherwise stop for review.

Acceptance tests: restart after each setup phase; timeout after each mutation; repeated confirmation; source data changes during review; expired two-minute confirmation window. Verify no duplicate side effects and no false “complete” status.

P1 — Evidence, reporting, and backup pipeline

Generate the source-preserving daily report, check database integrity, create a unique backup, verify it, and preserve configuration plus referenced calendar/strategy/data/model artifacts. Keep backups private and encrypted off-device according to the operator’s policy.

Acceptance tests: destination already exists, disk full, corrupted backup, missing artifact, wrong config, and restore to a separate path. A backup is only trustworthy after verification and periodic restore tests.

4. Important gaps and risks to verify in code

These are not all proven defects. They are risks suggested by the checklist that should be verified against the repository and tests.

Critical — No independent protection during service/feed failure

The checklist says the running server and usable quotes are needed for protection and fills. Confirm what actually happens during process crash, internet outage, broker disconnect, stale quotes, or illiquid/empty depth. Define alerting and escalation. Paper protection is not equivalent to broker-side protection in a live account.

Critical — Partial setup and ambiguous outcomes

The documented setup can partially persist and has no automatic rollback. Confirm operations are idempotent, run IDs are durable, state changes are auditable, and retries first inspect current state. Do not assume an error response means no mutation occurred.

High — Freshness and completeness are not a single invariant

The workflow depends on current-day source snapshots, the latest completed session, history coverage, calendar correctness, and per-symbol price-basis review. Create explicit validators for each. Keep source timestamp, market session date, download date, and review date distinct.

High — Authentication is not unattended

An expired token should block the relevant workflow and notify the operator. Retain normal broker login and 2FA. Avoid insecure token persistence, logging secrets, or retry loops that can cause account/session issues.

High — Exit request vs. actual exit

Confirm the ledger distinguishes requested, accepted, partially filled, filled, rejected, cancelled, and unresolved orders. Keep residual exposure visible at shutdown and across restart. Long-term and intraday accounts must use different closing policies.

Medium — Restore and disaster-recovery proof

The checklist describes backup verification but does not establish that a full restore is routinely tested. Add scheduled restore drills into a separate location and validate accounting, configuration, strategy artifacts, and report reproducibility.

Medium — Auditability

Each decision should be reconstructable from: account/config version, strategy profile, data-run ID and hashes, source timestamps, calendar version, readiness reasons, operator approval, order intent, order/fill identifiers, and actual fees/results.

Medium — Monitoring coverage

The checklist notes that UI polling occurs about every three seconds while visible and hidden tabs stop polling. Do not depend on browser polling as the sole monitor. Monitoring and alerts should run server-side or in a separate supervisor.

5. Suggested target architecture

  1. IST-aware scheduler: exchange calendar, run ID, deduplication, deadlines, and missed-run handling.
  2. Read-only preflight: service/account identity, broker status, calendar/notices, source freshness, history coverage, catalog, held-symbol coverage, outstanding orders and reviews.
  3. Preparation worker: download and validate data, produce exclusions/provenance, prepare review summary.
  4. Authorization gate: show exact policy, dates/hours, shortlist, retained holdings, basis reviews, and changes; require explicit approval according to a documented policy.
  5. Execution supervisor: mode/readiness checks, quote freshness, exposure/risk checks, order lifecycle reconciliation, protective-exit monitoring, pause handling.
  6. Evidence pipeline: daily report, integrity verification, backup, artifact manifest, notifications, and restore drills.

All phases should have durable statuses, timestamps, bounded retries, idempotency, and structured error codes. If a safety condition is uncertain, block new discretionary entries and ask for review rather than inventing evidence or changing state blindly. Do not use a generic kill/flatten action as a routine recovery mechanism.

6. Recommended implementation sequence

  1. Observe before acting: structured health/readiness endpoint, status report, logs, and alerts. No change to trading behavior.
  2. Automate read-only checks: source/date validation, quote freshness, order reconciliation reports, daily summary.
  3. Automate repeatable preparation: scheduled download and review-package generation, but stop at the authorization gate.
  4. Make recovery reliable: durable orchestration, idempotent mutations, interrupted-run detection, state-aware retries, and restore drills.
  5. Evaluate narrowly scoped automation: only after fault-injection tests, explicit operator authorization policy, and a tested rollback/recovery plan.
  6. Before live trading: independently validate broker semantics, real execution behavior, risk controls, outage handling, and accounting. Paper tests do not prove profitability or live-market safety.

7. Questions for a repository-level audit

  • Is there a supported health/readiness API or CLI that avoids scraping UI state?
  • Are all state-changing operations idempotent or protected by idempotency keys?
  • Can an order submission time out after the server has accepted it? How is that reconciled?
  • Are mode changes, setup confirmation, and protective exits durably audited?
  • Does a feed disconnect or stale quote block new entries independently of the browser?
  • Are quote freshness and price-basis rules enforced server-side at order submission time?
  • Can a scheduler safely run twice or resume after restart without duplicating work?
  • Do backup commands have side effects on pending orders or recovery state?
  • Is the full installation recoverable from a tested backup set, not just the database?
  • Are there fault-injection tests for process crash, clock skew, missing calendar data, corporate actions, partial fills, and broker timeouts?

9. Scope and confidence

Directly supported by the uploaded checklist: current manual workflow, daily strategy-data requirements, documented session/authentication behavior, setup confirmation boundary, feed/quote checks, order/fill distinctions, intraday versus long-term close behavior, and report/backup instructions.

Recommendations/inferences from this review: prioritization of automation, watchdog architecture, idempotency requirements, acceptance tests, target readiness report, and the repository audit questions.

Not established by the document: that the code contains a specific bug, that any suggested API exists, that the broker feed is entitled/healthy on a given day, that a strategy is profitable, or that the system is safe for real-money trading. Those require repository inspection, tests, and independent validation.

Conclusion

The best next step is to turn the checklist into a machine-readable daily runbook with durable statuses and evidence, automate read-only validation and reporting first, and preserve human approval for setup and trading authority. The most important engineering work is robust monitoring and state-aware recovery—not merely scripting the UI clicks.
